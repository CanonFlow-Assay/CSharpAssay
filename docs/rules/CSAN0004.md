# CSAN0004 — A public core contract exposes nullable data

Status: Admitted. Effective severity follows the shared core/shell/default policy.

## What caused the finding, and why it matters

A public contract contains an annotated nullable value, possibly nested inside
a generic type. A consumer must handle an extra absence case whose meaning may
not be part of the declared domain contract.

## Before

```csharp
#nullable enable
public sealed record SearchResult(string? Name);
```

## After

```csharp
#nullable enable
public sealed record SearchResult(string Name);
```

## Inspection and limits

The analyzer inspects public symbol nullability recursively for return values,
parameters, properties, fields, events and nested type arguments, with the
existing inherited/generated contract handling. The after-example is appropriate
only when Name is required: validate/reject untrusted input at the boundary.
If absence is valid, give it an explicit native domain case instead. Removing
`?` does not add runtime validation or prove that every object is valid. A public
non-nullable contract and compiler evidence are not a business correctness proof.

## Framework boundary

A serializer/ORM's nullable wire/storage contract can stay in a declared shell,
which converts it once to the actual core contract. Do not move arbitrary domain
behavior there to obtain Pass. Analyzer and verifier share the boundary policy;
solution verification checks the evaluated graph separately. Default is not shell.

## Code fix and compatibility

No automatic fix. Contract changes can break callers, API schemas, database
mapping and serializers. Check input-handling semantics and required tests.
Replacing checks with `!` erases compiler evidence and is a separate finding.

## Evidence and grants

Executable specimens: `specimens/Native.Good/CSAN0004/` and
`specimens/Native.Bad/CSAN0004/`; focused tests compile and analyze both examples.
Only an exact fingerprinted owner/reason/expiry grant authorizes suppression.
