# CSAN0001 — Nullable-flow evidence is disabled

Status: Admitted. Disabled nullable flow also leaves compiler evidence incomplete.

## What caused the finding, and why it matters

The compilation lacks the full nullable context, or source contains
`#nullable disable`. The compiler then cannot supply the nullable-flow evidence
required by this policy. Annotations-only and warnings-only modes are not the
full enabled context.

## Before

```csharp
#nullable disable
public static class Names
{
    public static int Length(string name) => name.Length;
}
```

## After

```csharp
#nullable enable
public static class Names
{
    public static int Length(string name) => name.Length;
}
```

## Inspection and limits

The rule reads compilation nullable options and disable directives. Enable
`<Nullable>enable</Nullable>` at project scope as well; the tiny example isolates
the directive. Fix resulting warnings by checking inputs or modeling absence.
Enabling the compiler does not prove runtime input is non-null or all paths safe.
Validate untrusted data at a real boundary; `!` erases evidence instead.

## Framework boundary

Framework nullable DTOs can stay in a declared shell and map into the core.
Keep flow analysis enabled there too: a shell or grant does not manufacture the
missing compiler evidence. Never move arbitrary domain behavior to avoid this
requirement or disable warnings to obtain green output.

## Code fix and compatibility

No automatic fix. Enabling nullable analysis can reveal existing warnings and
change annotated contracts. Review callers and framework mapping and run tests.

## Evidence and grants

Executable specimens: `specimens/Native.Good/CSAN0001/` and
`specimens/Native.Bad/CSAN0001/`; these snippets compile in focused tests.
A grant cannot turn absent compiler evidence into a verified application.
