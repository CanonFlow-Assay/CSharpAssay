# CSAN0002 — The null-forgiving operator removes compiler evidence

Status: Admitted. Effective severity follows the shared core/shell/default policy.

## What caused the finding, and why it matters

A postfix `!` suppresses nullable-flow warnings without checking the value.
It performs no runtime assertion. A null value can still reach the next access.

## Before

```csharp
#nullable enable
internal static class Names
{
    internal static int Length(string? input) => input!.Length;
}
```

## After

```csharp
#nullable enable
internal static class Names
{
    internal static int Length(string? input) => input is string value ? value.Length : 0;
}
```

## Inspection and limits

Roslyn identifies suppress-nullable-warning expressions where they occur in
analyzed source. Generated code is handled by the existing generated-code policy.
This example explicitly chooses zero for absence; it is not a universal business
rule. If absence is a distinct outcome, convert it into a native domain case.
Public nullable core contracts are checked separately by CSAN0004. A control-flow
check is evidence for that branch, not proof of every caller or business invariant.

## Framework boundary

Check untrusted transport/serializer values in a declared shell and map them to
validated core values. Retain domain decisions in the core. Shell scope reflects
a real framework responsibility, not permission to move arbitrary code until a
finding disappears. Avoid replacing the compiler warning with `!`.

## Code fix and compatibility

No automatic fix. Decide the missing-value outcome and test callers, rather than
blindly inserting a throw, default string or condition that changes behavior.

## Evidence and grants

Executable specimens: `specimens/Native.Good/CSAN0002/` and
`specimens/Native.Bad/CSAN0002/`; focused tests compile and analyze both examples.
Suppression needs the exact fingerprint and reviewed owner/reason/expiry grant.
